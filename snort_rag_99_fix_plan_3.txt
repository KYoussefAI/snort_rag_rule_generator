1. Executive Summary
The project is already above average because it contains a personal dataset, multiple retrieval strategies, a
Gradio dashboard, a local Snort-like rule parser, generated artifacts, false-positive heuristics, and honest
limitations. However, it cannot be considered 99/100 strict-compliant until it satisfies the instructor's central
missing requirements: real LLM generation inside RAG, LLM benchmarking, clustering/family attack analysis,
real/log-PCAP validation evidence, and final documentation cleanup.
The professor's Subject 2 asks for a system using NLP and RAG to automatically generate Snort rules from
natural-language descriptions of suspicious network behavior. It specifically requires retrieval with
Sentence-BERT/BM25, embedding benchmarking, an LLM generation module using the query plus retrieved
documents, LLM benchmarking, classification and clustering, rule explanations, false-positive optimization,
integration with real network logs, a dashboard with PDF upload, a personally constructed dataset, code,
and a technical report. [P1]
The project currently says that it is not a direct external-LLM workflow and that generation is done by
retrieved-rule selection or deterministic templates. This protects against black-box copying, but it leaves the
formal LLM requirement unsatisfied. In modern RAG, the user query and retrieved information are supplied
to an LLM before the final answer is generated, so a purely template-based generator should be
repositioned as a baseline or fallback, not the main final module. [W4]

4.4 Required prompt contract
The prompt must never ask the LLM to invent external knowledge. It must bind the model to the retrieved
Snort examples, the local syntax constraints, and the requested output schema. The prompt must be logged
in the returned result for auditability.
SYSTEM:
You are a defensive IDS rule assistant. Generate exactly one educational Snort rule.
Use only the user request and the retrieved documents. Do not invent CVEs, sources,
or runtime validation results. If the traffic is benign, output NO_RULE_RECOMMENDED.
RETRIEVED CONTEXT:
For each Top-k document include: id, attack_type, attack_family, log_example,
snort_rule_reference, false_positive_context, expected_explanation, retrieval_score.
OUTPUT JSON ONLY:
{
  "attack_type": "one allowed label",
  "generated_rule": "Snort rule or NO_RULE_RECOMMENDED",
  "explanation": "short technical explanation",
  "false_positive_notes": "why it is or is not broad",
  "used_source_doc_ids": ["SNORT-P1-...."],
  "confidence": 0.0
}
4.5 Validation and repair loop
1 Call the LLM once with the enriched prompt.
2 Parse JSON. If JSON fails, extract a single rule between markers or ask a repair prompt.
3 Validate the rule using rule_parser.validate_rule. Also ensure attack_type is allowed and source_doc_ids
are in retrieved docs.
4 If invalid, send one repair prompt containing validation errors and the original retrieved context.
5 If still invalid, fall back to the deterministic template and mark
generation_mode="template_fallback_after_llm_failure". Do not hide fallback.
6 Return prompt, model_name, generation_mode, repair_attempts, validation_errors, rule, explanation,
source_doc_ids, FP analysis, latency.

10. P1 - Snort Rule Quality and Parser Improvements
The rule generation is educational and structurally validated. To reach 99/100, make the rules closer to
Snort 3 best practices and make the parser stricter. Official Snort documentation distinguishes the rule
header from the rule body and emphasizes that options make the rule target the right traffic. [W1]
10.1 Parser improvements
Parser area Required improvement
Rule grammar Parse action, protocol, source net, source port, direction, destination net, destination
port, and option body into structured fields.
Option syntax Check that options are separated by semicolons and key/value options use colon
where required.
Required metadata msg, sid, rev, classtype required for malicious rules.
HTTP web attacks Require flow:to_server,established and an HTTP sticky buffer or service:http where
appropriate.
Rate-based attacks Require detection_filter for brute force, port_scan, icmp_sweep, malware_c2 beaconing
unless justified.
Benign handling NO_RULE_RECOMMENDED is valid only when attack_type is benign_traffic.
Duplicate SID Validate uniqueness across generated and exported rules.
Severity mapping Ensure classtype aligns with attack_family and severity.
10.2 Snort 3 HTTP buffer improvements
For URI-based web attacks, prefer explicit HTTP sticky buffers. Snort 3 supports http_uri and http_raw_uri;
http_uri searches normalized URI data, while http_raw_uri searches the unnormalized URI and is useful for
percent-encoded traversal. [W2]

This is a defensive cybersecurity project. Codex should avoid turning the project into an attack-generation
tool. Payload strings used for rule matching and PCAP simulation should be minimal, controlled, and
educational. The system should generate detection logic, not exploitation instructions.
